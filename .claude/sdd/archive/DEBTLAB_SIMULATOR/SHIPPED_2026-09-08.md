## 1. Summary

Primeiro simulador determinístico do projeto (`SIM-002 — DebtLab`, `SPEC-010`, `PRD-004`) — prova
o padrão "núcleo determinístico, borda probabilística" (`ADR-013`/`ADR-042`) que nenhuma das 6
features anteriores havia tocado, todas de ingestão de dado observado. Escolhido entre os 24
simuladores do catálogo por ser o que melhor aproveitava dado real já carregado (dívida e
resultado primário), mas a descoberta real revelou que faltava PIB — o usuário rejeitou
explicitamente uma simplificação sem ele ("incluir tudo que falta para entregar dados reais"),
expandindo o escopo para incluir ingestão real de PIB + Dívida Bruta do Governo Geral (BCB SGS,
séries 4380/13762) e Monte Carlo (`SPEC-016`) já no V1, não deixado para depois.

**Achado real que mudou o desenho antes de construir:** `divida_consolidada`
(`MVP_WALKING_SKELETON`) não é a métrica certa para "base debt/GDP" — é dívida estadual sob o PAF
(2022), um conceito diferente da dívida bruta nacional do governo geral que `SIM-002` precisa.
Corrigido com a métrica certa (`divida_bruta_pib`) em vez de forçar a errada a servir um propósito
para o qual não foi feita.

**Primeira permissão de escrita da API.** As 6 features anteriores deixaram a API 100%
somente-leitura (`api-runtime` = "read-only on Gold"). `POST /v1/simulations/debtlab` é o primeiro
endpoint que grava — permissão nova escopada só a `br2036_control` (least-privilege), CORS ganhou
`POST`. Persistência de cenário em BigQuery, não AlloyDB: `ADR-004` decidiu AlloyDB para estado
operacional, mas nunca foi provisionado em nenhuma das 6 features — provisionar agora (custo fixo,
sem approval workflow real que justifique) contradiria `ADR-002` (serverless-first). `ADR-059`
formaliza sem superar `ADR-004`.

**Achado real não planejado, corrigido no mesmo dia (PR #33):** minutos depois do merge do PR2, o
primeiro `POST /v1/simulations/debtlab` real em produção retornou 500 —
`bigquery.QueryJobConfig(maximum_bytes_billed=None)` serializa o campo como a string literal
`"None"`, que o BigQuery rejeita para um campo `INT64`. Corrigido no mesmo dia, com teste de
regressão verificado tanto contra o padrão com bug quanto contra o fix.

A revisão independente de `/verify-spec` re-derivou a fórmula do engine à mão e bateu exatamente
contra o código e a saída real da API — nenhum valor fabricado, nenhum selo `SIMULATED` incorreto.
2 achados reais corrigidos (formato de timestamp inconsistente entre `POST`/`GET`; uma frase
imprecisa no próprio `BUILD_REPORT` sobre o comportamento do bug corrigido).

## 6. Lessons learned

1. **Technical — um bug de serialização de biblioteca pode passar por todos os testes unitários com mock e só aparecer no primeiro `INSERT` real.** `bigquery.QueryJobConfig(maximum_bytes_billed=None)` serializa o campo como a string `"None"` em vez de omiti-lo — um comportamento que nenhum teste com `MagicMock` pegaria, porque o mock nunca inspeciona `to_api_repr()` a menos que o teste peça explicitamente. A lição generaliza: quando um parâmetro tem um valor sentinela especial (`None` = "desligado"), vale testar explicitamente o que a biblioteca real faz com esse valor, não só que o parâmetro "chegou" no objeto certo — e, quando possível, um teste de integração contra o serviço real (não só contra BigQuery-real-mas-dataset-isolado) teria pego isso mais cedo. Esta fatia não tinha um teste de integração cobrindo o *path de escrita* (só o de ingestão), diferente do path de leitura que todas as fatias anteriores já cobriam bem.

2. **Technical — antes de reaproveitar uma métrica existente, confirmar que ela é conceitualmente a mesma coisa, não só um dado "parecido".** `divida_consolidada` e "dívida bruta do governo geral" soam relacionados (ambos são "dívida pública"), mas são estatísticas de fontes, metodologias e escopos territoriais completamente diferentes (PAF estadual 2022 vs. governo geral nacional mensal). A descoberta real no `/design` (chamar a API do BCB de verdade, não supor) pegou isso antes de construir em cima da métrica errada — reforça o padrão já estabelecido nas fatias anteriores de nunca supor formato/semântica de dado sem inspecionar de verdade.

3. **Process — a sequência de decisões do usuário durante o `/brainstorm` (rejeitar a simplificação 2 vezes) foi o sinal mais forte de escopo desta fatia, mais forte que a recomendação inicial do agente.** A primeira proposta era um V1 simplificado (sem PIB, sem Monte Carlo) — o usuário rejeitou ambas as simplificações explicitamente, pedindo "tudo que falta pra entregar dados reais". Vale documentar esse padrão: quando o usuário rejeita uma simplificação oferecida como recomendação, não insistir nela numa reformulação diferente — a rejeição já é o sinal de que o escopo maior é o que ele quer.

4. **Communication — corrigir uma frase imprecisa no próprio relatório de build é tão importante quanto corrigir o código.** O achado #2 do `/verify-spec` não era um bug de código — era uma explicação errada de *por que* uma escolha de teste foi feita (a alegação de que a propriedade Python "normaliza pra `None`" era falsa; na verdade levanta `ValueError`). A escolha de teste em si já estava certa, só a justificativa documentada estava errada. Isso reforça que documentação técnica merece o mesmo rigor de verificação que código — uma afirmação sobre comportamento de biblioteca deveria ser testada, não assumida, mesmo em um comentário/relatório.
