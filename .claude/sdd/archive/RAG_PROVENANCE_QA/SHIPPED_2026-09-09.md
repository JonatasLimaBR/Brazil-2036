## 1. Summary

Primeira capability de RAG do projeto (`EPIC-024 — Knowledge/RAG`, `SPEC-018`, `ADR-026`) — até
esta fatia, 0% construído. Em vez de partir para descoberta de documentos legais/fiscais novos
(LOA/decretos/DOU — domínio totalmente não tocado), o usuário ancorou esta 1ª fatia no que o
projeto já tem de real: as 7 fatias de dado já shipadas deixaram `metric_provenance`/
`dataset_registry` cheios de URLs oficiais reais por métrica, mas sem nenhum texto explicativo de
metodologia. Esta fatia entrega `POST /v1/knowledge/ask`: retrieval híbrida (vetor + metadata)
sobre um corpus de 11 parágrafos de metodologia curados manualmente (1 por `metric_id` já real),
com um gate de evidência 100% determinístico (`ADR-013`) e síntese de resposta via Gemini
(`google-genai`, 1ª chamada de IA generativa que o projeto faz em produção) restrita ao contexto
que o gate já validou como relevante.

**Arquitetura sem serviço novo, mesmo padrão já estabelecido:** retrieval 100% dentro do BigQuery
(`VECTOR_SEARCH` sem `CREATE VECTOR INDEX` + filtro de metadata) em vez de Vertex AI Vector Search
dedicado — mesmo racional que já rejeitou AlloyDB no `DEBTLAB_SIMULATOR` (`ADR-059`). Só uma
conexão IAM nova (BigQuery↔Vertex AI) foi provisionada.

**2 bugs reais de produção, ambos corrigidos no mesmo dia:**
1. (PR2) `refresh_embeddings()` filtrava `WHERE embedding IS NULL` — testado ao vivo antes de
   escrever o resto do pipeline (disciplina já estabelecida): BigQuery armazena um `ARRAY<FLOAT64>`
   `NULL` como array vazio (`[]`), nunca `NULL` de verdade — o filtro combinaria zero linhas para
   sempre, um no-op silencioso permanente. Corrigido para `ARRAY_LENGTH(embedding) = 0 OR ... IS
   NULL`.
2. (PR4, hotfix pós-deploy do PR3) 1ª chamada real de `POST /v1/knowledge/ask` em produção 500ou —
   `roles/aiplatform.user` (para a chamada direta ao Gemini) não bastava; faltava
   `bigquery.connections.use` do `api-runtime` na conexão `rag-vertex-ai` (3ª identidade de IAM
   distinta desta integração — a SA da própria conexão, `api-runtime` chamando Gemini diretamente,
   e `api-runtime` usando a conexão dentro de uma query, cada uma com seu próprio grant).

A revisão independente de `/verify-spec` verificou os 8 acceptance tests ao vivo em produção
(incluindo o caso negativo — pergunta fora do corpus retornando "evidência insuficiente" sem nunca
chamar o LLM), confirmou estruturalmente que o gate determinístico é genuíno (não só documentado),
e confirmou a precisão dos 2 bugs relatados contra o código/Terraform real. 1 achado real: o
requisito MUST de retrieval híbrida (`DEFINE` G4) incluía `SEARCH()`/full-text, que foi
silenciosamente reduzido a só vetor+metadata durante o build, documentado depois do fato só no
`SPEC-018` — corrigido com uma decisão rastreada explícita em `ADR-061`/`BUILD_REPORT` antes do
`/ship` (não bloqueava nenhum AT, mas uma redução de escopo de um requisito MUST nunca deveria
ficar sem registro rastreável).

## 6. Lessons learned

1. **Technical — integrar BigQuery com um serviço externo via `REMOTE WITH CONNECTION` envolve até
   3 identidades de IAM distintas, não 1.** A service account da própria conexão (autentica contra
   o serviço externo), o principal que executa a query (precisa de `bigquery.connections.use` no
   recurso da conexão), e, se houver uma chamada direta separada ao mesmo serviço fora do BigQuery,
   uma permissão própria para essa chamada. As 3 vêm de decisões de IAM diferentes — supor que 1
   implica as outras foi exatamente a causa do hotfix do PR4. Vale generalizar para qualquer
   integração futura de BigQuery com um modelo remoto.

2. **Technical — testar uma combinação de SQL nova contra o serviço real antes de escrever o
   módulo em cima dela evita repetir bugs já vistos.** Dado que a sessão já tinha visto 2 bugs
   reais de SQL em `MACRO_TWIN_EXPANSION`, a combinação `VECTOR_SEARCH` + filtro NULL-ável foi
   testada ao vivo antes de virar código — passou sem surpresa, mas a disciplina de testar antes
   (não só depois) é o que realmente evita repetir o padrão, não a sorte.

3. **Process — uma decisão de reduzir o escopo de um requisito MUST precisa de um registro
   rastreável no momento em que é tomada, não só uma menção retroativa no SPEC.** O achado do
   `/verify-spec` (queda do `SEARCH()`/full-text) não era um bug funcional — a decisão em si era
   defensável (corpus pequeno, vetor sozinho já cobre bem) — mas ficou sem rastro até a revisão
   independente notar. A lição: toda vez que o build se afasta de um MUST do `DEFINE`, isso precisa
   virar uma linha na tabela de Autonomous Decisions do `BUILD_REPORT` no momento em que a decisão
   é tomada, não só quando alguém de fora perguntar por quê.

4. **Communication — "descoberta real" às vezes significa criar um recurso de nuvem pra testar, não
   só ler uma API pública.** Toda descoberta real anterior do projeto (BCB, Tesouro, INSS) foi
   feita chamando APIs públicas sem provisionar nada. Esta fatia foi a 1ª vez que a única forma
   real de confirmar um comportamento (`ML.GENERATE_EMBEDDING` funciona a partir de
   `southamerica-east1`?) exigia provisionar um recurso de verdade — resolvido isolando isso como
   o PR1 do build (uma fatia mínima, barata de reverter, verificada ao vivo antes de qualquer
   código de retrieval/endpoint depender dela), em vez de assumir e descobrir o problema só depois
   de todo o pipeline estar escrito.
